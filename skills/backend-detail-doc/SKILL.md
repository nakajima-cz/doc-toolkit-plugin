# バックエンド詳細設計書生成スキル

既存のバックエンドソースコードを関数・メソッド単位で解析し、詳細設計書を生成する。

## 事前準備

作業開始前に、以下の設定ファイルを読み込んでください:

- `.claude/project-config.md` — バックエンド構造、関数ディレクトリ、IaC定義ファイル位置

## 既存スキルとの違い

| 観点 | api-doc-generator | このスキル (backend-detail-doc) |
|------|-------------------|-------------------------------|
| 目的 | API仕様の共有・連携 | 実装の理解・保守・引き継ぎ |
| 粒度 | エンドポイント単位 | 関数・メソッド単位 |
| 読者 | API利用者・フロント開発者 | 同じコードを触る開発者 |
| コード参照 | なし | ファイルパス・行番号を全セクションで併記 |
| Input/Output | リクエスト/レスポンスのみ | 暗黙的Input・副作用・ログ出力まで網羅 |

## 対象プロジェクト構造

バックエンド構造は `.claude/project-config.md` の「バックエンド構成」を参照。
一般的には以下のパターン:

```
backend-directory/
├── function/          # 関数群
│   ├── feature-1/     # API系
│   ├── batch/         # バッチ処理
│   ├── queue/         # メッセージキュー処理
│   └── ...
├── template.yaml      # IaC定義（.claude/project-config.md で指定）
├── layer/             # 共通レイヤー
└── lib/               # 共通ライブラリ
```

## 解析ワークフロー

### Step 1: 対象の特定と分類

ユーザーの指示から対象を特定し、以下のいずれかに分類する:

- **API関数**: HTTPリクエストをトリガーとする関数（IaC定義のAPI Gatewayイベント）
- **バッチ処理**: スケジュール / cron トリガーの関数
- **メッセージキュー処理**: メッセージキューをトリガーとする関数
- **統合処理**: 外部システム連携

分類によって Input/Output セクションのフォーマットが変わる。

### Step 2: エントリポイント解析

対象バックエンド関数のハンドラファイルを読み、以下を特定する:

1. ハンドラのシグネチャと位置（行番号）
2. イベント引数からのパラメータ取得パターン
3. 呼び出している内部メソッド・共通ライブラリ
4. エラーハンドリング処理

### Step 3: Input解析

関数の分類に応じてInputを網羅する:

**API関数の場合**:
- リクエストヘッダー（認証トークン等）
- パスパラメータ / クエリパラメータ / リクエストボディ
- 各フィールドの型・必須/任意・制約・検証箇所
- 暗黙的Input: JWTクレーム、DBからの参照データ、環境変数

**バッチ処理の場合**:
- トリガーイベント（スケジュール式、定義箇所）
- 環境変数（IaC定義から抽出）
- 処理対象データ（DBクエリ条件、取得カラム、想定件数）

**メッセージキュー処理の場合**:
- メッセージ構造（送信元のenqueue箇所から推定）
- 環境変数
- 処理対象データ

### Step 4: 処理フロー解析

ハンドラの処理を上から順に追い、ステップごとに分解する:

- 各ステップのコード範囲（行番号）を記録
- ビジネスロジックの条件分岐を追跡
- DB操作（テーブル名、CRUD種別、条件）を記録
- 外部API呼び出し、SQS送信を記録
- 共通ライブラリの参照があれば `layer/` や `lib/` まで追跡

### Step 5: Output解析

関数の分類に応じてOutputを網羅する:

**API関数の場合**:
- 成功レスポンス: ステータスコード、全フィールド（型・説明・生成箇所）
- エラーレスポンス: 条件・ステータス・レスポンス・発生箇所
- 副作用: DB更新、SQS送信、外部API呼び出し

**バッチ処理の場合**:
- DB更新: テーブル・操作・更新内容・条件・発生箇所
- メッセージキュー送信: キュー名・メッセージ構造・送信条件
- ログ出力: レベル・内容・条件・発生箇所
- 関数戻り値: 正常/異常時の戻り値

### Step 6: 依存関係整理

- DB操作一覧（テーブル・操作・箇所）
- 共通ライブラリ一覧（モジュール名・用途・パス）
- 外部連携一覧（SQS、外部API等）

### Step 7: ドキュメント生成

`references/backend-detail-template.md` のテンプレートに従って出力する。


## コード参照の表記ルール

全セクションで以下の表記を使用し、コードの場所を併記する:

| 表記 | 意味 |
|------|------|
| `backend/function/feature/handler.rb:12` | 特定行 |
| `backend/function/feature/handler.rb:12-28` | 行範囲 |
| `backend/function/feature/handler.rb` | ファイル全体 |
| `:12` | 同一ファイル内での短縮表記（直前にフルパスが記載されている場合） |

行番号は解析時点のものであり、この旨をドキュメント冒頭に注記すること。

## スコープ指定

- **関数指定**: 「feature/handler の詳細設計書」→ 該当関数のみ
- **機能カテゴリ指定**: 「機能A関連の詳細設計書」→ 関連ディレクトリ配下の全関数
- **種別指定**: 「バッチ処理の詳細設計書」→ バッチ処理の全関数
- **全体**: 対象が多い場合はまず一覧を提示し確認を取る

1つの詳細設計書は1つのバックエンド関数（または密接に関連する関数群）を対象とする。複数関数を一括で指定された場合は関数ごとに個別ファイルで出力する。

## 注意事項

- ソースコードから推定できない情報は「要確認」と明記する
- 共通ライブラリへの参照は必ずパスまで追跡する。追跡できない場合は「layer/lib 未特定」と記載
- バリデーション制約は実装コードから正確に抽出する。推測で制約を追加しない
- 処理フローは実装順序に従う。理想的な順序に並べ替えない
- レスポンス例のデータは実装から推定可能な範囲で生成し、推測部分は `/* 推定 */` とする
