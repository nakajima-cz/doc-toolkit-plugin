# バックエンド実装スキル

バックエンドコードの新規作成・改修を行い、完了後に関連する設計書を自動更新する。

## 事前準備

作業開始前に、以下のファイルを読み込んでください:

- `.claude/project-config.md` — 技術スタック、ディレクトリ構造、ファイル配置ルール、認証方式

`project-config.md` の先頭に `CONFIG_STATUS: UNCONFIGURED` が含まれている場合は作業を開始せず、
`project-setup` スキルを実行するようユーザーに案内してください。

---

## 動作モード

ユーザーの指示から自動的にモードを判定します。

| モード | 判定条件 | フロー |
|---|---|---|
| **code-first** | 「〇〇を実装して」「APIを追加して」「バグを直して」等、要件・タスクを直接記述 | 要件分析 → 【確認①】実装計画 → コード実装 → 変更ファイル記録 → 設計書更新委譲 |
| **doc-first** | 「この設計書を元に実装して」「設計書に合わせてコードを修正して」等、設計書を起点に記述 | 設計書解析 → 差分分析 → 【確認①】実装計画 → コード実装 → 整合確認 |

---

## code-first モード

### Step 1: 要件分析

ユーザーの指示から以下を明確にする:

- 実装対象（新規 API / 既存 API の改修 / バッチ処理 / キュー処理 / モデル変更 等）
- 影響するファイル（ハンドラ / サービス / モデル / 共通ライブラリ / IaC定義）
- DBの変更が伴うかどうか（マイグレーション要否）

不明な点があればこの時点でユーザーに確認する。実装を開始してから仕様が変わると手戻りが大きいため、
曖昧な要件は必ず解消してから次のステップへ進む。

### Step 2:【確認①】実装計画の提示

以下の形式で実装計画を提示し、ユーザーの承認を得る。
**ユーザーが承認するまで、いかなるコードの書き込みも行わない。**

```
## 実装計画

### なぜこの実装アプローチか
{設計上の判断・選択肢の比較・トレードオフを自然言語で説明する。
 例: 「既存の service クラスを拡張する方針をとります。新規クラスを作るよりも
     既存の認証・エラーハンドリングの仕組みを再利用できるためです。」}

### 作成・修正するファイル
| 操作 | ファイルパス | 変更内容の概要 |
|---|---|---|
| 新規作成 | {path} | {概要} |
| 修正 | {path} | {概要} |

### DBの変更
{マイグレーションの内容、または「なし」}

### 影響する設計書（実装後に更新予定）
- {doc_path}: {更新内容の概要}

この計画で実装を進めてよいですか？
```

### Step 3: コード実装

承認を得たらコードを実装する。
以下の「コーディング規約」を必ず遵守すること。

### Step 4: 変更ファイルの記録

実装完了後、変更したすべてのファイルを以下の形式で整理する:

```
変更ファイルリスト:
- {path}（新規作成）
- {path}（修正）
```

### Step 5: 設計書の自動更新

`doc-sync` スキルを即時モード（`--immediate` フラグ）で呼び出し、設計書更新を委譲する。
doc-sync への指示テンプレート:

```
以下のファイルが変更されました。関連する設計書を即時同期モードで更新してください。

【変更ファイルリスト】
{変更ファイル一覧}

即時同期モードで実行してください（git履歴ではなくこのリストを参照する）。
更新内容の差分をユーザーに提示し、確認を得てから更新を適用してください。
```

## doc-first モード

### Step 1: 設計書の読み込みと解析

指定された設計書を Read し、以下を抽出する:

- 実装すべきエンドポイント / 関数 / 処理の一覧
- 入力仕様（リクエスト形式・パラメータ・型・バリデーション制約）
- 出力仕様（レスポンス形式・ステータスコード・エラーパターン）
- DB操作（テーブル名・CRUD種別・条件）
- 認証・認可要件

### Step 2: 現状コードとの差分分析

対応するソースファイルが存在する場合は読み込み、設計書との差分を分析する:

| 状況 | 対応 |
|---|---|
| 設計書にあるがコードにない | 新規実装が必要 → 実装計画に追加 |
| コードが設計書と異なる振る舞いをしている | 修正が必要 → 実装計画に追加 |
| コードにあるが設計書に記載がない | ユーザーに確認（仕様漏れ or コード側の独自追加） |

### Step 3:【確認①】実装計画の提示

code-first モードと同形式で提示する。加えて、設計書との対応関係を表で明示する:

```
### 設計書 → コード 対応マップ
| 設計書の記述 | 実装ファイル | 変更内容 |
|---|---|---|
| POST /cart/items の処理フロー | backend/function/cart/handler.rb | add_item メソッドを新規追加 |
```

### Step 4: コード実装

code-first モードと同じ「コーディング規約」で実装する。

### Step 5: 設計書との整合確認

実装完了後、以下の観点で設計書と照合する:

- 設計書に記載されたすべての仕様がコードに反映されているか
- コードの振る舞いが設計書の記述と一致しているか

差分が残っている場合はユーザーに以下のいずれかを提案する:

1. コードを設計書に合わせて修正する（設計書が正）
2. 設計書をコードの実装に合わせて更新する（実装都合で仕様変更が発生した場合）

## コーディング規約（必須）

すべての実装でこの規約を遵守すること。

### 1. 実装意図のコメント

各ファイルの先頭、または各メソッド・クラスの直前に、その実装の意図と設計判断を記述したコメントを追記する。
コードを読むだけでは伝わらない「なぜそうしたか」を必ず残す。

```ruby
# == カートハンドラ ==
#
# カートに関するAPIリクエストのエントリポイント。
# バリデーション → 認証 → ビジネスロジックの順で処理を進める。
#
# NOTE: クーポン適用ロジックは apply_coupon_service.rb に委譲している。
#       カート計算の責務をここに集約しないための設計判断。
#
# TODO: 在庫チェックを非同期化する（現在は同期処理で遅延が発生しうる）
def handler(event:, context:)
```

### 2. TODO / NOTE / FIXME / HACK コメント

将来の対応が必要な箇所・既知の制約・暫定対応には、必ずタグ付きコメントを残す。

```ruby
# TODO: バリデーションエラーメッセージを国際化対応する（i18n未対応）
# NOTE: このメソッドはスレッドセーフではない。並列実行環境では呼び出し側で制御すること
# FIXME: エラー時のロールバック処理が不完全。トランザクション見直しが必要
# HACK: 外部APIのレスポンス形式変更に伴う暫定対応。v2 移行後に削除する
```

### 3. 可読性優先のコーディング

簡潔さよりも読みやすさを優先する。以下の方針に従う:

**命名は省略せず、意図が伝わる名前にする**

```ruby
# 良い例
cart_item_count = cart.items.count
is_over_item_limit = cart_item_count > MAX_CART_ITEMS

# 悪い例（何をチェックしているか一読では分からない）
flag = items.count > 50
```

**マジックナンバーは定数に切り出してコメントを付ける**

```ruby
# 良い例
MAX_CART_ITEMS = 50  # カートに追加できる商品の上限（仕様書 §3.2 参照）

# 悪い例
if items.count > 50
```

**ネストが深い処理はメソッドに切り出して平坦化する**

```ruby
# 良い例: 処理の意図がメソッド名で伝わる
def handler(event:, context:)
  params = extract_and_validate_params(event)
  user   = authenticate_user(event)
  result = apply_coupon_to_cart(user, params)
  build_success_response(result)
end

# 悪い例: ネストが深く全体の流れが追いにくい
def handler(event:, context:)
  if event['body']
    params = JSON.parse(event['body'])
    if params['coupon_code']
      user = verify_token(event['headers']['Authorization'])
      if user
        # ...深いネストが続く
```

**複雑な条件式はローカル変数か述語メソッドに切り出す**

```ruby
# 良い例
user_can_add_item = user.active? && !cart.locked? && cart.items.count < MAX_CART_ITEMS
raise CartError, "追加不可" unless user_can_add_item

# 悪い例
raise CartError, "追加不可" unless user.active? && !cart.locked? && cart.items.count < 50
```

### 4. プロジェクト固有の規約遵守

`project-config.md` に記載された以下を必ず参照・遵守する:

- ハンドラのシグネチャ（関数の入口の書き方）
- 認証検証関数の使用方法とロール定義
- 共通ライブラリのパスとインポート方法
- エラーレスポンスのフォーマット

## 注意事項

- 既存ファイルを修正する前に必ず Read して現状を把握してから手を入れる
- 認証・認可処理は `project-config.md` に記載の認証検証関数を正しく使用する
- DB操作を伴う場合、トランザクション処理の要否を確認する
- 環境変数の追加が必要な場合は IaC 定義ファイル（template.yaml 等）にも追記する
- テストファイルの作成・更新が必要かどうかはユーザーに確認してから行う
- ソースコードから判断できない仕様は「要確認」と明記し、推測で実装しない
