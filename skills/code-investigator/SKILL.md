# コード調査・ドキュメント化スキル

## 事前準備

作業開始前に、以下の設定ファイルを読み込んでください:

- `.claude/project-config.md` — プロジェクト構造、ドキュメント出力ディレクトリ

曖昧な質問や調査依頼を受け、既存ドキュメントとソースコードを横断的に調査し、回答とドキュメント化を行う。

## 既存スキルとの違い

| 観点 | 詳細設計書系スキル | このスキル (code-investigator) |
|------|-----------------|------------------------------|
| トリガー | 「設計書を作って」 | 「〇〇を調べて」「〇〇の仕組みは？」 |
| 入力 | 明確な対象指定 | 曖昧・投げやりなクエリ |
| 参照元 | ソースコードのみ | 既存ドキュメント → ソースコード（段階的） |
| 出力形式 | テンプレート準拠の設計書 | 質問に最適化された調査レポート |
| 保存先 | `.claude/project-config.md` 指定のドキュメント出力ディレクトリ | 調査レポート保存ディレクトリ（`.claude/project-config.md` 参照） |

## 調査ワークフロー

### Step 1: クエリ解釈

ユーザーの質問から調査対象と調査スコープを特定する。

**質問パターンと解釈戦略**:

| パターン | 例 | 解釈 | 調査アプローチ |
|---------|-----|------|-------------|
| 機能名ベース | 「チケット配送を調べて」 | キーワードで横断検索 | Grepでキーワード検索 → 関連ファイル特定 |
| ディレクトリベース | 「cart周りの仕組み」 | 指定ディレクトリ配下を調査 | Glob + 各ファイルRead |
| ファイル指定 | 「この関数何してる？」 | 指定ファイルを解析 | 直接Read |
| ユースケースベース | 「管理者がユーザーを停止する流れ」 | 処理フローを端から端まで追跡 | APIエントリポイント → DB → 画面 |
| アーキテクチャ | 「SQSで何が流れてる？」 | 特定技術要素を横断調査 | template.yaml + Grep |
| 状態・データ | 「チケットのステータスは？」 | DB定義 + 状態遷移を調査 | db_scheme.sql + コード内の状態更新箇所 |
| 比較・関係 | 「AとBの違いは？」 | 2つの機能を対比 | 両方を調査し差分を整理 |

**曖昧な場合の対応**:
- 質問が漠然としすぎて調査範囲が特定できない場合は、候補を提示して確認する
- ただし、ある程度推定可能なら確認せず調査を開始する（投げやりな質問への対応が目的のため）

### Step 2: 類似レポートの確認とユーザーへの確認

**必ず最初に** 調査レポート保存ディレクトリ（`.claude/project-config.md` 参照）を探索し、
今回の調査と類似・重複するレポートがないかを確認する。

**確認手順**:
1. 調査レポートディレクトリ配下のファイル一覧を Glob で取得
2. ファイル名とキーワードで類似レポートを特定
3. 候補ファイルを Read して調査範囲の重複度を評価

**判定基準**:

| 重複度 | 判断 | アクション |
|-------|------|-----------|
| 同一テーマのレポートが存在する | **更新候補あり** | ユーザーに確認してから進む |
| 関連するが別テーマ | 新規作成 or 統合 | ユーザーに確認してから進む |
| 類似レポートなし | 新規作成 | そのまま調査を開始 |

**ユーザーへの確認メッセージ例**（類似レポートがある場合）:

```
類似の調査レポートが見つかりました:
- `[report-xxx].md`（概要: 〇〇の調査、調査日: YYYY-MM-DD）

どちらで進めますか？
1. 既存レポートを更新する（重複排除・可読性ルール適用）
2. 新規レポートとして別ファイルを作成する
```

**更新を選んだ場合**:
- 既存レポートを全文 Read してから調査・統合を行う
- 重複セクションは統合し、新情報を追記する
- 可読性ルール（目次・章立て・道案内文）を遵守する
- 調査日を更新する

### Step 3: 既存ドキュメント検索

生成済みドキュメントを優先的に参照する。

**検索順序**:
1. 調査レポート保存ディレクトリ — 過去の調査レポート（Step 2 で確認済み）
2. バックエンドドキュメントディレクトリ — 詳細設計書・API設計書
3. フロントエンドドキュメントディレクトリ — 画面設計書
4. ER図・その他設計資料

（各ディレクトリはと `.claude/project-config.md` で指定）

**検索方法**:
- Glob で対象ディレクトリのファイル一覧を取得
- ファイル名からキーワードマッチ
- 候補ファイルを Read して関連性を確認
- 関連するドキュメントが見つかった場合、その内容をベースに回答を構成

**既存ドキュメントがある場合**:
- ドキュメントの内容を要約・引用して回答
- ドキュメントへの参照リンクを記載
- 不足情報があればStep 4でソースコード調査を補完

**既存ドキュメントがない場合**:
- Step 4に進み、ソースコードから直接調査

### Step 4: ソースコード調査

既存ドキュメントで不足する情報をソースコードから補完する。

**調査手順**:

1. **キーワードGrepで関連ファイルを特定**
   - 関数名、テーブル名、パス名等をGrepで全ファイルから検索
   - IaC定義ファイル（`.claude/project-config.md` 参照）からAPI/バッチの定義を検索
   - スキーマ定義ファイルからテーブル定義を検索

2. **エントリポイントの特定**
   - API: IaC定義 → バックエンド関数ハンドラ
   - バッチ: スケジュール定義 → バックエンド関数ハンドラ
   - メッセージキュー: キュートリガー → メッセージコンシューマ
   - 画面: フロントエンドのルーティング定義箇所

3. **処理フローの追跡**
   - エントリポイントから処理を追い、関連する処理を芋づる式に発見
   - 共通ライブラリへの呼び出しも追跡
   - DB操作、メッセージキュー送信、外部API呼び出しを記録
   - 全箇所のファイルパス・行番号を記録

4. **横断的関連の調査**
   - 調査対象の機能に関連する他の機能を発見
   - 例: 購入API → 配送SQS → 配送バッチ → 配送失敗通知メール
   - 関連テーブル、関連画面を含めて全体像を把握

### Step 5: 回答生成

調査結果を会話内で即座に回答する。

**回答の構成**:
1. **サマリー**（2-3文で結論を先に伝える）
2. **関連コンポーネント一覧**（全体像を俯瞰）
3. **詳細説明**（質問の核心に応じた深掘り）
4. **要確認事項**（ソースから読み取れなかった点）

### Step 6: ドキュメント化

回答内容を調査レポートとしてファイルに保存する。

**保存先**: `.claude/project-config.md` の「ドキュメント出力設定」に指定された調査レポート保存ディレクトリ
**ファイル名**: `[対象キーワード].md` または `investigation-[対象キーワード].md`
  - 例: `ticket-delivery.md`、`cart-flow.md`
  - 例: `investigation-admin-user-ban.md`

**保存方針**（Step 2 の確認結果による）:
- **更新の場合**: 既存レポートを全文 Read し、新情報と統合した上で全体を書き直す。重複セクションを排除し、可読性ルールを適用する
- **新規作成の場合**: 指定された命名規則に従い新規ファイルを作成する

出力フォーマットは `references/investigation-template.md` に従う。

#### 関連ドキュメントの deeplink 設定（必須）

レポート保存後、調査中に参照・言及した関連ドキュメントとの間に **Obsidian wiki リンク**（`[[ファイル名（拡張子なし）]]`）を双方向で設定する。

**対象となる関連ドキュメント**:
- 調査中に参照した他の調査レポート
- 調査対象の API 詳細設計書
- 調査対象の画面仕様書

**手順**:

1. **新規レポートのヘッダーに参照先リンクを追記**

   フロントマターの直後（`## 目次` より前）に `関連ドキュメント` セクションを設け、参照先を列挙する:

   ```markdown
   ## 関連ドキュメント

   - [[sync-agent-full]]
   - [[sync-schedule-state]]
   ```

2. **参照先ドキュメントにも逆リンクを追記**

   参照先のドキュメントを Read し、既存の `関連ドキュメント` セクションがあれば追記、なければ追加する:

   ```markdown
   ## 関連ドキュメント

   - [[sync-schedule-state-inventory]]  ← 追記
   ```

   - 調査レポートの場合: `## 目次` の直前に挿入
   - API 詳細設計書等の場合: ファイル末尾に追加

**注意事項**:
- リンクはファイル名のみ（拡張子 `.md` は不要）
- ディレクトリパスも不要（Obsidian はファイル名で解決する）
- 既にリンクが存在する場合は重複追加しない

#### 可読性ルール（必須）

**1. 目次（Table of Contents）**

調査対象が6節以上、または複数コンポーネントを横断する場合は目次を必ず冒頭に記載する。

```markdown
## 目次

1. [全体アーキテクチャ](#1-全体アーキテクチャ)
2. [ComponentA — 副題](#2-componenta--副題)
...
```

**2. 章立て（番号付き節構成）**

複数コンポーネントを扱う場合、節に番号を振り副題（ダッシュ区切り）を付ける。

```markdown
## 1. 全体アーキテクチャ
## 2. SyncAgentFunction — 委託先同期 + エンキュー
## 3. SyncItemFunction — 商品・催事・スケジュール同期
```

**3. 節冒頭の道案内文**

各節の冒頭に、その節が何を説明するかを1〜2文で記述する。
読者が詳細を読む前に「何のセクションか」を把握できるようにする。

```markdown
## 2. SyncAgentFunction — 委託先同期 + エンキュー

**ファイルパス**: `backend/function/sync_agent/app.rb`

> 委託先（agents）をTicketHubから取得してDBに同期し、後続の商品同期ジョブをSQSにエンキューする起点バッチ。
> 毎日UTC 17:00 に実行される。
```

**4. 全体アーキテクチャセクション**

複数バッチ・API・DBが登場する調査では、最初のセクションに以下を置く:
- **テキストダイアグラム**: コンポーネント間の依存関係をASCII図で表現
- **一覧表**: 全コンポーネントの役割・実行タイミングを表で整理

**5. マッピング表の統合**

TicketHub → DB のフィールドマッピングは、各節の詳細とは別に「全体マッピング表」セクションをまとめて設けると参照しやすい。

**6. 比較表**

2つ以上のコンポーネントに共通の観点がある場合（例: 来場予約 vs イベント予約）、専用の比較セクションを設ける。

## コード参照の表記ルール

全セクションで以下の表記を使用:

| 表記 | 意味 |
|------|------|
| `backend/function/feature/handler.rb:12` | 特定行 |
| `backend/function/feature/handler.rb:12-28` | 行範囲 |
| `backend/function/feature/handler.rb` | ファイル全体 |
| `:12` | 同一ファイル内での短縮表記 |


## 注意事項

- 投げやりな質問に対応するスキルであることを意識する。ユーザーに過度な情報提供を求めない
- 推測で回答を構成しない。ソースから確認できない情報は「要確認」と明記
- 調査範囲が広大になりそうな場合は、まず概要を回答し、深掘りしたい部分をユーザーに確認する
- 既存ドキュメントを引用する際は、そのドキュメントが最新かどうかの注意を記載する
- 同じ機能について複数回調査された場合、過去の調査レポートを参照・統合する
